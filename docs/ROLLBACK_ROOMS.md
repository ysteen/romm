# RomM rollback rooms

The v2 player offers multiplayer rooms for SameBoy (GB/GBC), mGBA Splitscreen (GBA), and Snes9x (SNES) when the independent RetroArch netplay bridge is configured. Every participant runs the game locally; the bridge carries inputs and synchronization messages. The existing SNES in-game **Netplay** button opens this room flow when the bridge is enabled. Without it, the existing streaming entry remains available.

| System | Qualified core version                     | Room content and save behavior                                                                                                                 |
| ------ | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| GB/GBC | SameBoy `1.0.4c87d256-rollback2`           | Two copies of the same cartridge; each web participant imports and saves their own battery data.                                               |
| GBA    | mGBA Splitscreen `0.1.0-f1d5975-rollback1` | Two to four copies of the same cartridge; each web participant has their own save slot. The current live UI qualification covers two players.  |
| SNES   | Snes9x `1.632d4cce69`                      | One cartridge and two joypads; the host supplies the shared initial save. Both participants can save the shared progress to their own account. |

SNES rooms currently accept standard, non-interleaved **NTSC LoROM/HiROM** cartridges up to 4 MiB with an unambiguous valid header. Raw `.sfc`/`.smc` and ZIP archives containing one cartridge are supported, including 512-byte copier headers. PAL, extended/interleaved images, and ambiguous or invalid headers are rejected before starting a room. The qualified frontend clock is NTSC; PAL timing must be implemented and verified before enabling it.

Open the room from the v2 game page, create it, and share its **room invitation** and **room password** separately. Web invitations require access to that game through a RomM account. A running single-player session uploads its current battery save before the room fetches the server copy; an unsuccessful upload stops the handoff while preserving the original player's automatic saving.

Native guests start from the room host's synchronized machine state; importing a native guest's separate personal battery save is not implemented. Web GBA rooms accept compatible raw saves from both `mgba` and `mgba_splitscreen`, seed from the most recently updated compatible save, and write progress to the room's own core/slot. Other cross-core battery imports are not qualified.

Each room displays its RetroArch server address and port, matching core version, and core download. The packaged native downloads are **Linux x86_64 only**. Install the provided core through RetroArch's **Load Core → Install or Restore a Core**, load the same cartridge (in every link slot for handheld cores), and connect through Netplay with the room password. SameBoy uses 48000 Hz audio. The RetroArch application itself does not require modification. Android and Windows binaries are not included or qualified by this integration.

Dedicated assets live below `custom-emulatorjs/data/cores/compat/rollback/`. Each package includes the matched WASM bundle, Linux core, upstream license, source revision, patch where needed, `BUILD.txt`, and a SHA-256 manifest. Existing single-player and standalone handheld link assets remain available through their previous paths.

## Reproducible integration verification

Run `node scripts/verify-rollback-rooms.mjs` from the RomM repository with the prepared diagnostic cartridges and cached headless browser. The script imports the real independent broker from the sibling `retroarch-netplay-bridge` directory; `NETPLAY_BRIDGE_SOURCE` overrides that location. `NETPLAY_UI_SYSTEMS=gb,gba,snes` selects systems, and `NETPLAY_UI_OUTPUT` changes the evidence directory. RomM's authenticated HTTP API is mocked per account; the broker, WebSocket transport, installed core packages, cartridge extraction, core state, rendering, audio, and save bytes are real.

The recorded run in `result/netplay-interop/romm-rollback-rooms/result.json` passed all three systems at **603 confirmed frames per peer**, with byte-identical confirmed states and 10 CRC checks per peer. Forty-millisecond remote-input delivery delays produced six host and two guest rollbacks per system. Both keyboard seats, gamepad input, real touch events on the virtual A button, touch pause, local audio, and per-account SRAM uploads passed. The SNES fixture was loaded through a real ZIP extraction worker, and both accounts preserved the host's shared SRAM seed. Dark and light layouts fit widths from 320 to 3840 pixels.

After building the production frontend, run `node scripts/verify-bridge-launcher.mjs` to check the actual v2 launcher. Its recorded **12 scenarios passed**: configured and unavailable room buttons, both themes, mouse, Tab/Enter, trusted touch, standard Gamepad API activation, and layouts at 320, 768, 1280, and 1920 pixels. The ordinary SNES player boots the real qualified Snes9x WASM package; its Netplay toolbar pauses the core and completes the SRAM upload before the room handshake. This also passed when the broker configuration response was delayed by three seconds and Play was pressed before it arrived. The script uses isolated HTTP API fixtures and a popup handshake recorder; room networking is covered by the separate test above. It disables the optional screen Wake Lock API in headless Chrome, makes no deployment requests, and closes the browser on completion. Evidence and screenshots are in `result/netplay-interop/romm-bridge-launcher/`; `NETPLAY_LAUNCHER_OUTPUT` overrides this directory.

These results cover original diagnostic cartridges and a two-browser room. Longer native RetroArch qualification and standalone broker CI are documented in the independent project's qualification report. They do not establish compatibility for every commercial game or additional GBA player counts. The browser is always closed in `withHeadlessBrowser`'s cleanup, and the three systems run sequentially to limit memory use.
